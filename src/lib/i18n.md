# Locale strategy (i18n scaffold)

Only English (`en-US`) ships today. The site is structured so adding a locale
is a ~1-day task with no redesign.

## Where strings live

- UI chrome strings: `src/messages/<locale>.json` (keyed by content ID,
  e.g. `nav.solutions`). `en.json` is the reference catalogue.
- Content data (`src/data/*.ts`): hardcodes English today. To localize, move
  each record's copy into the catalogue and resolve via a
  `getMessages(locale)` loader — the type shapes in `src/types/content.ts`
  stay unchanged.
- Code rule: no bare `.toLocaleString()`. Use `formatDate` / `formatNumberIntl`
  from `src/lib/i18n.ts` with an explicit locale argument.

## Adding a locale (checklist)

1. Copy `src/messages/en.json` → `src/messages/<locale>.json`, translate values
   (keys frozen).
2. Add the locale to `supportedLocales` in `src/lib/i18n.ts`.
3. Introduce an App Router `[locale]` segment under `src/app/` with
   `generateStaticParams` over the supported list; pass the locale into
   `formatDate`/`formatNumberIntl` call sites and `<html lang dir>`.
4. Verify RTL: set `dir="rtl"` on `<html>` and walk `/`, `/solutions/[slug]`,
   `/start-a-project`. Layout uses logical properties and direction-agnostic
   flex throughout, so navbar, hero, and cards must compose mirrored with no
   CSS changes. Record the pass here.

## Copy rules for translators

- No idioms, sports metaphors, or region-specific references.
- SI units only. Numbers keep `tabular-nums`.
- Forbidden-words list (`BRAND-GUIDE.md` §3) applies in every language —
  maintain a per-locale equivalent list.
- Disclaimers (`disclaimers.*` keys) must remain visible, never buried.

## Why no next-intl yet

Deliberate: a full `[locale]` router migration adds bundle and routing churn
for a single-language launch. The catalogue + explicit-locale helpers above
are the migration seam — adopting next-intl later means wiring its loader to
`src/messages/`, not rewriting components.
