# Locale strategy

Only English (`en-US`) ships. That is a decision, not an unfinished scaffold: a
half-wired message catalogue is worse than no catalogue, because it implies a
localization system that does not exist and lets copy drift out of sync.

## What was removed, and why

An earlier revision documented `src/messages/<locale>.json` as the home of the
UI strings and shipped an `en.json` catalogue. Nothing imported it. Its contents
had drifted away from what rendered — its `estimate` and `exampleArchitecture`
strings rendered nowhere at all, and the latter became a *third* wording of the
"example architecture" disclosure that `BRAND-GUIDE.md` then cited as the
approved one. Documentation said one thing, the catalogue said another, and the
UI said a third.

The catalogue is gone. Everything that is genuinely locale-bearing is below.

## What exists

- **Date and number formatting**: `formatDate` / `formatNumberIntl` in
  `src/lib/i18n.ts`, always with an explicit locale. Code rule: never a bare
  `.toLocaleString()`, which resolves against the visitor's environment and
  renders differently on different machines and CI runners.
- **Shared disclosure copy**: `src/data/disclaimers.ts`. These are the strings
  that must read identically everywhere, so they have one home enforced by
  `src/lib/__tests__/disclaimers.test.ts`.
- **Layout**: logical properties and direction-agnostic flex throughout. An RTL
  locale requires `dir="rtl"` and no CSS changes — see the verification log
  below, which is honest about the fact that this has not been walked yet.
- **Content**: `src/data/*.ts`, typed against `src/types/content.ts`, written in
  English inline.

## Adding a locale

1. Create `src/messages/<locale>.json` for UI chrome, and resolve it through a
   loader. Do not create it before there is a second locale — an unreferenced
   catalogue is how the previous one drifted.
2. Add the locale to `supportedLocales` in `src/lib/i18n.ts`.
3. Add an App Router `[locale]` segment under `src/app/` with
   `generateStaticParams` over the supported list, and pass the locale into
   `formatDate` / `formatNumberIntl` and `<html lang dir>`.
4. Move content strings out of `src/data/*.ts` into per-locale content modules,
   keeping the record shapes in `src/types/content.ts` unchanged.
5. Walk `/`, `/solutions/[slug]`, `/start-a-project` with `dir="rtl"` and record
   the result in the table below. Check specifically: the navbar dropdown
   origin, the article "on this page" rail, the intake wizard's directional step
   animation (it uses `x`, which is direction-dependent), and the footer columns.
6. Translate `src/data/disclaimers.ts` values, and add equivalents of the
   `BRAND-GUIDE.md` §3 forbidden-words list for the new language. Disclosures
   must stay visible in every locale; they are not optional copy.

## Why not `next-intl` yet

A full `[locale]` router migration adds routing and bundle churn for a
single-language launch. The helpers above are the migration seam: adopting it
later means wiring its loader to `src/messages/`, not rewriting components.

## RTL verification log

| Date | Routes | Widths | Result |
|---|---|---|---|
| 2026-10-25 | 12 (`/`, `/solutions`, `/solutions/ai-agents`, `/services`, `/industries/healthcare`, `/work/<slug>`, `/insights`, `/insights/<slug>`, `/start-a-project`, `/technology`, `/about`, `/security`) | 390, 1440 | **24/24 combinations: no horizontal overflow** under `dir="rtl"` |

Run it yourself with `npm run check:rtl` against a production build, or
`RTL_BASE=https://<host> npm run check:rtl` against a deployment. It exits
non-zero on any overflow.

What was actually changed to make that result mean something, rather than the
walk merely finding no overflow on a layout that was already symmetric:

- Direction-dependent utilities were converted to their logical equivalents —
  `text-left`/`text-right` → `text-start`/`text-end`, `pl-`/`pr-` → `ps-`/`pe-`,
  `ml-`/`mr-` → `ms-`/`me-`, `border-l` → `border-s`, and the insets that
  position content (the nav dropdown, the select chevrons, the currency and
  percent affixes inside the ROI fields, the back-to-top and cookie-banner
  corners, the skip link). In LTR these resolve to exactly the same box, which
  the 320px overflow tests confirm; in RTL they mirror, which is the point.
- The exit-intent prompt was centred with `left-1/2 -translate-x-1/2`, a physical
  transform that would push it off-centre in RTL. It now centres with
  `inset-x-0 mx-auto`, which needs no transform in either direction.
- The reading-progress fill used `origin-left`. No logical `transform-origin`
  exists in CSS, so the `.progress-fill` class sets it per direction in
  `globals.css`; otherwise the bar would read as filling backwards in RTL.

Remaining, and deliberately not changed:

- The intake wizard's step transition animates `x` from `+24px` (or `-24px` when
  moving back). Under RTL the sign should invert for the motion to read correctly.
  It is cosmetic, it affects only the animation direction, and Framer Motion has
  no direction-aware `x`; a locale-aware sign is a one-line change when a second
  locale actually exists.
- The trust-strip marquee translates by `-50%` regardless of direction, so it
  scrolls left-to-right in RTL. Its content is a repeated brand list with no
  reading order, and it is masked at both edges.
- No Arabic or Hebrew font is loaded, and no text shaping or `lang` switching has
  been exercised. A real RTL locale would need that before this log means
  "supported" rather than "does not break".
